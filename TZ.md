# Техническое описание проекта «Сортировщик почты»

Этот документ описывает текущую реализацию и известные ограничения. Это не обещание, что система уже готова к эксплуатации без наблюдения.

## Назначение

Приложение читает письма из выбранной IMAP-папки, классифицирует их по настроенным правилам и предлагает или выполняет перемещение в папку назначения. Оно рассчитано на один сервер Windows и несколько независимо настроенных почтовых ящиков. В составе приложения есть веб-интерфейс и фоновый опрос.

## Состав и порядок работы

1. Конфигурации ящиков загружаются из локальных `configs/*.yaml` или `configs/*.yml`.
2. IMAP-клиент устанавливает TLS-соединение с проверкой сертификата. Если у имени сервера несколько IP-адресов, он последовательно проверяет их, сохраняя исходное доменное имя для SNI и проверки сертификата.
3. Письма читаются без установки флага прочтения. Сейчас сортировщик берёт не более 100 писем за один проход.
4. Выбранный провайдер ИИ — локальная Ollama или Cloud.ru Foundation Models — получает текст письма и правила. Старые конфигурации без `llm.provider` используют Ollama.
5. Ответ модели должен содержать разрешённую категорию, уверенность и краткую причину. Неизвестная категория, некорректный ответ или техническая ошибка не приводят к перемещению. Корректный отказ от выбора категории и низкая уверенность направляют письмо в настроенную папку `unsorted_folder`.
6. В режиме **Dry Run**, который включён при каждом запуске по умолчанию, приложение показывает фактический целевой IMAP-путь и статистику, не изменяя письмо. Для режима **Active** требуется отдельное точное подтверждение администратора.

## Папки

Новые ящики используют `folder_layout: inbox`: простое имя категории становится подпапкой INBOX с разделителем, полученным от IMAP-сервера. Вложенные пути и кириллица поддерживаются через `imap-tools`. Ящики без этой настройки сохраняют прежнее размещение папок; явно указанные пути не переписываются.

На странице «Папки» администратор проверяет структуру и после отдельного подтверждения создаёт только недостающие папки. Обычный опрос не создаёт, не удаляет и не переименовывает папки. Удаление категории из правил не удаляет почтовую папку.

## Подтверждение перемещений

При поддержке сервером IMAP `MOVE` используется команда `UID MOVE`. Если сервер не поддерживает `MOVE`, безопасный резервный путь возможен только при `UIDPLUS`: `UID COPY`, `UID STORE` и адресный `UID EXPUNGE`. Общий `EXPUNGE`, способный затронуть другие письма, не применяется.

Если ответ на MOVE потерян или повреждён, приложение не повторяет перемещение вслепую. Оно проверяет результат через отдельное IMAP-соединение, учитывая `UIDVALIDITY` и признаки сообщения: UID в разных папках не считается одним идентификатором. Неопределённая операция записывается в локальный журнал `logs/move-pending-*.jsonl` и блокируется для автоматического повтора до ручной проверки.

На тестовом Exchange наблюдался `imaplib.IMAP4.abort` с кодом `unexpected_response` после фактически выполненного `UID MOVE`. Независимая проверка подтверждала результат. Точный формат отвергнутой серверной строки пока не установлен; для одного согласованного испытания предусмотрена явно включаемая структурная диагностика без записи сырого ответа. Порядок её включения приведён в `README.md`.

## Настройки и безопасность

- Пароль IMAP рекомендуется передавать через `ENV:MAIL_PASSWORD`. Старые конфигурации с открытым паролем загружаются для совместимости, но не должны публиковаться.
- Ключ Cloud.ru принимается только через `ENV:CLOUDRU_FOUNDATION_MODELS_API_KEY`; пример конфигурации не содержит ключа.
- Веб-сервер по умолчанию слушает `127.0.0.1`; административные запросы требуют авторизации, а операции с папками дополнительно защищены CSRF. Первоначальная настройка доступна только локально.
- Проверка TLS обязательна. Ошибка сертификата не приводит к переходу на небезопасное соединение.
- Текст письма считается недоверенными данными для модели. Секреты, ответы сервера и содержимое писем не должны попадать в диагностический журнал.
- Локальные конфигурации, журналы, виртуальное окружение и файлы ключей исключены из Git.

## Известные ограничения

- Систематический `abort` на тестовом Exchange ещё требует дополнительной диагностики; отсутствие ложных ошибок обеспечивается проверкой фактического результата, а не устранением первопричины.
- Нет SQLite-очереди, параллельной обработки и нагрузочных испытаний. Журнал неопределённых MOVE — отдельный защитный механизм, а не общая очередь писем.
- Вложения не используются при классификации; OAuth2 для IMAP не реализован.
- Active Mode следует включать только после проверки правил, структуры папок и результатов Dry Run на разрешённом тестовом ящике.

Установка, пример YAML, проверка модели и запуск тестов описаны в `README.md`.
